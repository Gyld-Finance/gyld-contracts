# Live-Anvil verification of the ERC-8056 lifecycle — 2026-07-31

First execution of the ERC-8056 (Scaled UI Amount) extension against a **running chain**.
`GyldBondToken`'s implementation and its 41 unit tests
(`contracts/test/GyldBondToken.ScaledUIAmount.t.sol`) landed in `0948e8d`, but until this
run no multiplier had ever been read, scheduled or activated on a live node: the previous
verification ([`anvil-verification-2026-07-31.md`](anvil-verification-2026-07-31.md)) covered
the GYL-1135 deploy hardening and never touched the UI multiplier.

Branch `feat/testnet-erc8056-atomic-swap`, base HEAD `bc810b5`. Foundry `forge 1.5.1-stable`,
`anvil/v1.5.1`.

**Why a separate document rather than a new section in the existing one.** The GYL-1135
record is a closed account of a different subject (deploy-script guard rails), and it
already numbers *its own* findings F-1/F-2/F-3 — which would collide head-on with the
ERC-8056 spec's F-1/F-2/F-3 remediation items referenced throughout this file. The existing
document is untouched apart from a one-line cross-reference.

**Two source changes were made as a result of this work**, both additive, neither weakening
a guard:

1. `contracts/script/DeployDevNet.s.sol` now wires `UI_MULTIPLIER_ROLE` (§4 — the role was
   granted by **no** committed deploy script).
2. `contracts/script/SepoliaErc8056Series.s.sol` and
   `contracts/script/SepoliaAtomicSwapSmoke.s.sol` gained chain guards and pre-flight
   assertions (§0 — they had **no chain guard at all**).

## Safety envelope

Every transaction in this document was broadcast to a **local Anvil node on
`http://127.0.0.1:8545`**. No public RPC was contacted and no real key was used — only
Anvil's published dev accounts, which are safe by construction.

Each driver script begins with a hard gate that aborts before any broadcast:

```bash
CID=$(cast chain-id --rpc-url $RPC)
CLIENT=$(cast client --rpc-url $RPC)
[ "$CID" = "31337" ] || { echo "ABORT: chain-id $CID != 31337"; exit 1; }
case "$CLIENT" in anvil/*) ;; *) echo "ABORT: client $CLIENT is not anvil"; exit 1;; esac
# => SAFETY OK: chain-id=31337 client=anvil/v1.5.1 rpc=http://127.0.0.1:8545
```

The gate is not decoration: mid-run the node died and the next invocation printed
`PRE-BROADCAST SAFETY: chain-id= client=` and refused to broadcast. Note also that an
unrelated `anvil --chain-id 11155111 --port 8546` was running on the same machine; every
gate above pins **both** the chain id and the port, so nothing in this run could reach it.

```bash
export RPC=http://127.0.0.1:8545
```

## 0. Review of the two pre-existing Sepolia scripts

`contracts/script/SepoliaErc8056Series.s.sol` and
`contracts/script/SepoliaAtomicSwapSmoke.s.sol` were untracked, auto-generated by an earlier

### Verdict: the ERC-8056 / swap logic is sound; the safety and re-runnability scaffolding was not

**Correct as written** (each verified against the contracts, not taken on trust):

| Claim in the script | Verified against |
| --- | --- |
| `deployToken(name, symbol, isin, maturity, operator, issuanceManager, navFeedOwner)` | `TokenFactory.sol:124` — arity and order match |
| routing `deployToken` / `upgradeToAndCall` / `grantRole` through the timelock | `TokenFactory._wireRoles` grants `DEFAULT_ADMIN_ROLE` to `owner()`, i.e. the timelock — so the timelock genuinely is the only caller that can upgrade or grant |
| bare `upgradeToAndCall(impl, "")` needs no initializer | `GyldBondToken._uiMultiplierState()` normalises the never-written slots; proven live in §1 |
| the four ERC-165 ids `0xa60bf13d / 0x4bd27648 / 0x57854fc3 / 0xd890fd71` | read out of `GyldBondToken.sol:24-58`; all four confirmed `true` live in §2.1 |
| `effectiveAt() == 0` is the correct post-upgrade sentinel | `GyldBondToken.sol:335`; confirmed live in §1d |
| BUY at `price = 1e28`: 2 USDC → 0.02 bonds sits exactly on NAV | `amountOut = 2e6 * 1e28 / 1e18 = 2e16`; `navValue = 2e16 * 100e8 / 1e20 = 2e6` — dead centre of the band |
| `balanceOfUI == raw * 1.05` after `setUiMultiplier(1.05e18)`, and 1.05x is inside the 10% cap | `2e16 * 1.05 = 21e15`; deviation `0.05e18 * 10000 = 500e18 ≤ 1e18 * 1000 = 1000e18` |
| scheduling `+2h` rather than `+1h` to clear `MIN_UI_MULTIPLIER_UPDATE_INTERVAL` | correct, and for the right reason — the floor is anchored to the previous **activation**, not the call time (`GyldBondToken.sol:530`) |

**Defects found and fixed:**

| # | Severity | Defect |
| --- | --- | --- |
| S-1 | **High** | **No chain guard whatsoever** in either script. A file named `Sepolia*` that reads its targets from env vars would have broadcast a real EIP-712-signed quote, a real UUPS upgrade and a real `subscribe` mint to whatever `--rpc-url` pointed at. Fixed: both now `require(block.chainid == DeployGuards.SEPOLIA_CHAIN_ID)`. Anvil is deliberately *also* rejected — every step depends on pre-existing live Sepolia infrastructure, so a local run could only fail half-way and leave a partly-configured series behind. |
| S-2 | Medium | **Every prerequisite was an unchecked assumption.** `SepoliaErc8056Series` assumed the timelock owns the factory, that `minDelay == 0` (it schedules and executes in one run), and that the deployer can propose *and* execute — none checked; a wrong `TIMELOCK` would fail deep inside a partially-completed batch. `SepoliaAtomicSwapSmoke` assumed the series was registered, the taker allowlisted, the swap a whitelisted AP, and that the deployer held `SUBSCRIBER_ROLE`, `QUOTE_SIGNER_ROLE` and `UI_MULTIPLIER_ROLE`. Fixed: named pre-flight `require`s, before `startBroadcast`. |
| S-3 | Medium | **The upgrade was never actually verified.** The script checked `uiMultiplier() == 1e18` — a value the *new* implementation returns by normalisation whether or not the upgrade landed, so the assertion could pass on an unchanged proxy. Fixed: assert the proxy's own ERC-1967 slot (`vm.load(proxy, 0x360894…2bbc) == address(newImpl)`), and log before/after. |
| S-4 | Medium | **Single-use by construction.** `SepoliaAtomicSwapSmoke` hard-coded `quoteId: 1` and asserted *absolute* balances (`balanceOf(deployer) == 2e16`, `usdc.balanceOf(swap) == 4e6`), so a second run — or any pre-existing balance — failed for the wrong reason. Fixed: `QUOTE_ID` env var checked unused up front, and all assertions are deltas against an entry snapshot. |
| S-5 | Low | **Timelock salts were positional** (`bytes32(uint256(1..3))`), so re-running with a different ISIN collided on operation ids. Fixed: salts derived from the ISIN. |
| S-6 | Low | **Undocumented env var** — `DEPLOYER` is read at line 37 but the header documented only `PRIVKEY / FACTORY / TIMELOCK / ISSUANCE_MANAGER`. Fixed, plus a `vm.addr(pk) == deployer` cross-check. |
| S-7 | Low | Log said `scheduled 1.04x in 1h` while the code scheduled `+2 hours`. Fixed. |
| S-8 | **Documentation, but important** | **All the `require`s are simulation-time assertions.** `forge script` runs `run()` against a simulated fork, collects the state-changing calls, and only then broadcasts. Every `require` therefore gates the *simulated* outcome and proves nothing about the broadcast result; worse, `block.timestamp` inside an assertion is the *simulation* clock, so `require(token.effectiveAt() == block.timestamp + 2 hours)` cannot hold on-chain. The scripts read as on-chain verification and are not. Fixed: documented prominently in both headers, and each now prints the `cast call` commands to re-verify against the live node after mining. |

Neither script was executed *by this verification* — they target Sepolia and this run was
local-only. (A parallel effort did run their pre-hardening versions on Sepolia; see the
concurrency note in §6.) §1–§3 below re-prove the same properties on Anvil with `cast`,
which is stronger evidence than a simulation-time `require`.

## 1. The E-F1 upgrade window, against a real pre-ERC-8056 proxy

GYL-1136 requires that "the E-F1 upgrade window must be closed before any live proxy is
upgraded", and noted it was untested against a real pre-upgrade proxy. The in-suite F-1
tests (`test_f1_legacyProxyStorageImage_isNeverReadableAsZero` and friends) synthesise the
zero state with `vm.store`; this section does the real thing — an actual pre-ERC-8056
implementation, behind an actual ERC-1967 proxy, with live balances, upgraded on a live
node.

### Fixture

The pre-ERC-8056 implementation is the parent of `0948e8d`:

```bash
git show 3507f1b:contracts/GyldBondToken.sol   # 253 lines, no ERC-8056 anything
```

It was compiled in a **throwaway forge project outside the repo** (renamed
`GyldBondTokenV1` so nothing can collide) rather than copied into `contracts/`, so no
duplicate implementation is left behind. Storage compatibility is exact — both files carry
the identical ERC-7201 root:

```
0x0fe35ba304a016e79d78a184eb899c1e21310138e0bfe9a54648a2dfe0da0d00
```

`initialize(string,string,string,uint256,address,address,address)` is byte-identical
between the two versions, so the proxy's init calldata is the real thing.

### 1a–1b. A realistic pre-upgrade proxy with live state

```
PRE-8056 impl (V1)          = 0xcf7ed3acca5a467e9e704c703e8d87f634fb0fc9
PROXY                       = 0xdc64a140aa3e981100a9beca4e685f962f0cf6c9

V1 impl uiMultiplier() -> Error: execution reverted, data: "0x"      # the function does not exist

PRE-UPGRADE  name        = "Gyld Pre8056 Series"
PRE-UPGRADE  isin        = "US0000000001"
PRE-UPGRADE  totalSupply = 1250000000000000000000
PRE-UPGRADE  bal(A0)     = 1000000000000000000000
PRE-UPGRADE  bal(A1)     = 250000000000000000000
PRE-UPGRADE  impl slot   = 0x…cf7ed3acca5a467e9e704c703e8d87f634fb0fc9
```

The three ERC-8056 fields sit at offsets 3/4/5 of the namespaced struct and were never
written by the old implementation — this is the exact storage image the window is about:

```
slot base+3 (0x…0d03) = 0x00…00
slot base+4 (0x…0d04) = 0x00…00
slot base+5 (0x…0d05) = 0x00…00
```

Every ERC-8056 read fails on the pre-upgrade proxy, as it must:

```
uiMultiplier()       -> execution reverted, data: "0x"
newUIMultiplier()    -> execution reverted, data: "0x"
effectiveAt()        -> execution reverted, data: "0x"
balanceOfUI(address) -> execution reverted, data: "0x"
```

### 1c. The bare upgrade — no initializer calldata

```
ERC-8056 impl (V2) = 0x2279b7a0a67db372996a5fab50d91eaa73d2ebe6
upgrade tx         = 0xb4243ddccdf30c3f4848d073ad1aee11125c97898590b8cbe446b50f5cb9a045
post-upgrade impl slot = 0x…2279b7a0a67db372996a5fab50d91eaa73d2ebe6
```

`upgradeToAndCall(newImpl, 0x)` — deliberately empty calldata. There is no atomic
follow-up call, so if a window existed this is where it would be observable.

### 1d. **RESULT: the window does not exist.** The multiplier initialises safely

```
uiMultiplier()     = 1000000000000000000     <- 1e18, NOT 0
newUIMultiplier()  = 1000000000000000000
effectiveAt()      = 0                       <- sentinel: nothing ever scheduled
toUIAmount(1e18)   = 1000000000000000000
fromUIAmount(1e18) = 1000000000000000000     <- would PANIC 0x12 if the multiplier were 0
```

And the raw slots are **still all zero** — the upgrade wrote nothing; `_uiMultiplierState()`
normalises on read, which is why no post-upgrade transaction is required and the upgrade
need not be atomic:

```
slot base+3 = 0x00…00
slot base+4 = 0x00…00
slot base+5 = 0x00…00
```

This is the load-bearing point. A `0` multiplier would make `balanceOfUI` report **zero for
every holder** and make `fromUIAmount` revert with a division-by-zero panic (`0x12`). It
reads 1.0x instead, which is also the *correct* value rather than a safe guess: pre-upgrade
balances were never scaled, so 1.0x reproduces the exact pre-upgrade display.

Pre-existing state survived the upgrade untouched:

```
name        = "Gyld Pre8056 Series"        totalSupply = 1250000000000000000000
bal(A0)     = 1000000000000000000000       balanceOfUI(A0) = 1000000000000000000000
bal(A1)     =  250000000000000000000       balanceOfUI(A1) =  250000000000000000000
                                           totalSupplyUI() = 1250000000000000000000
```

### 1e. No window in which an unprivileged caller can set the multiplier

`UI_MULTIPLIER_ROLE` is held by nobody after the upgrade — not even the proxy's
`DEFAULT_ADMIN`:

```
hasRole(UI_MULTIPLIER_ROLE, A0 /* DEFAULT_ADMIN */) = false
hasRole(UI_MULTIPLIER_ROLE, A1 /* unprivileged  */) = false
```

Every attempt reverts (`0xe2517d3f` = `AccessControlUnauthorizedAccount(address,bytes32)`;
the second word is `keccak256("UI_MULTIPLIER_ROLE")` =
`0xaeb2a04b5c0b03314842538e4cbd28316edd6ab050cf7939cb4fb49cae3766c6`):

```
A0 setUiMultiplier(1.05e18)      -> 0xe2517d3f 000…f39fd6e5…  aeb2a04b5c0b0331…
A1 setUiMultiplier(1.05e18)      -> 0xe2517d3f 000…70997970…  aeb2a04b5c0b0331…
A1 scheduleUiMultiplier(1.05e18) -> 0xe2517d3f 000…70997970…  aeb2a04b5c0b0331…
A1 upgradeToAndCall(V1, 0x)      -> 0xe2517d3f 000…70997970…  0000…0000  (DEFAULT_ADMIN_ROLE)
```

The removed F-2 reinitializer is genuinely gone from the deployed implementation — an
anyone-callable `reinitializer(2)` could otherwise have been front-run to burn the version
slot and block every future v2 migration:

```
A1 initializeUiMultiplierV2() -> execution reverted, data: "0x"   # selector does not exist
```

**Conclusion: the E-F1 window is closed on a real pre-upgrade proxy.** A live series can be
upgraded with a bare `upgradeToAndCall(impl, "")`, in one transaction, with no follow-up and
no exposure.

Taker returned to `balanceOf = 10000000000000000000` and `usdc = 99000000000`, i.e. the
round trip settled at par despite a 1.10x display multiplier.

### 3.5 — a UI-priced quote is *rejected*, which proves the band measures raw units

A confused integrator reading `balanceOfUI` would see "11 tokens" and ask 1100 USDC for
`10e18` bonds. The NAV band refuses it:

```
BUY 1100 USDC -> 0x09b1bbd1  QuotePriceOutOfBand(quoted=1100000000, navValue=999999999)
```

`navValue` is computed from `balanceOf`-denominated units × NAV, so the 2% band caps the
quote at ~1020 USDC. Verdict: **the multiplier did not leak into settlement, pricing, or
the NAV band.**

## 4. Closing the deploy-wiring gap (GYL-1136)

### The gap

`grep -rn UI_MULTIPLIER_ROLE contracts/script/` returned **nothing**.
`TokenFactory._wireRoles` grants `MINTER_ROLE`, `BURNER_ROLE`, `PAUSER_ROLE` and
`DEFAULT_ADMIN_ROLE` and stops. So on the normal deploy path *no address ever held
`UI_MULTIPLIER_ROLE`*: the ERC-8056 multiplier was permanently pinned at 1.0x on every
series, and there was no key able to publish a new one. §1e is the live confirmation —
after a correct upgrade the role is held by nobody, including `DEFAULT_ADMIN`.

### The wiring

`contracts/script/DeployDevNet.s.sol`:

- new `Config.uiMultiplierAdmin`, resolved with
  `DeployGuards.envAddressProdRequired("UI_MULTIPLIER_ADMIN", c.navFeedOwner)` — the
  existing house pattern. The fallback is **`NAV_FEED_OWNER`, not the deployer**: the
  multiplier is a display mirror of that feed's NAV and belongs to the same publisher
  identity, so a deployment that sets `NAV_FEED_OWNER` correctly cannot accidentally leave
  this role on the deployer EOA;
- `DeployGuards.requireNotDeployer(c.uiMultiplierAdmin, c.deployer, "UI_MULTIPLIER_ADMIN")`;
- `_grantUiMultiplierRole()` schedules and executes the grant **through the timelock**,
  which holds `DEFAULT_ADMIN_ROLE` on each token after `TokenFactory._wireRoles`;
- deployed series are recorded in `bondTokens` / `bondTokenCount()`;
- `_assertUiMultiplierRole()` added to the in-band post-deploy assertions (inside the
  broadcast, so a mismatch aborts the deploy): role granted to the configured admin, not
  held by the deployer on production, `uiMultiplier() == 1e18` and `effectiveAt() == 0`;
- Phase-2 instructions for production now include the per-series grant, with the role id.

`.env.example` gained `UI_MULTIPLIER_ADMIN` inside the `all [PROD-REQUIRED]` block.

`contracts/test/DeployScripts.t.sol` gained three scenarios:
`reject_devNet_uiMultiplierAdminIsTheDeployer`,
`accept_devNet_uiMultiplierRoleIsWiredOnEverySeries`,
`accept_devNet_uiMultiplierAdminDefaultsToNavFeedOwner`.

Both directions were mutation-checked. Removing the grant:

```
[FAIL: DeployDevNet: UI_MULTIPLIER_ROLE not granted on a series]
```

Removing the `requireNotDeployer` guard:

```
[FAIL: expected run() to revert with: UI_MULTIPLIER_ADMIN must not be the deployer EOA]
```

### Live verification

`DeployDevNet` broadcast to Anvil with `UI_MULTIPLIER_ADMIN=0x90F79bf6…3b906` (acct[3]) and
`NAV_FEED_OWNER` deliberately set to a *different* address, so the grant cannot pass by
coincidence:


## 7. Summary

- **The E-F1 upgrade window is closed**, proven against a real pre-ERC-8056 implementation
  behind a real ERC-1967 proxy with live balances, upgraded on a live node with bare
  `upgradeToAndCall(impl, "")`. `uiMultiplier()` reads `1e18`, never `0`; the raw slots stay
  zero and are normalised on read; pre-existing state is untouched; no unprivileged caller
  can set the multiplier at any point, and the removed F-2 reinitializer is absent.
- **The full lifecycle works on a live chain**: four ERC-165 ids, role gating, pending vs
  active schedule, an activation boundary pinned exactly at `effectiveAt`, both guards
  (10% deviation and 1h interval) firing at their exact edges, `ZeroMultiplier`,
  `UiMultiplierEffectiveAtInPast`, and `TransferWithUIAmount` with the canonical topic0 and
  the correctly scaled payload.
- **The core invariant holds**: `balanceOf` and `totalSupply` returned byte-identical values
  at 1.0x, 1.05x, 1.155x and 1.2x, while `balanceOfUI` and `totalSupplyUI` scaled exactly.
- **Settlement is unaffected by the multiplier**: the identical BUY produced
  `amountOut = 10000000000000000000` at both 1.0x and 1.10x, REDEEM settled at par, and a
  UI-priced quote was correctly rejected with `QuotePriceOutOfBand`.
- **The deploy-wiring gap is closed**: `UI_MULTIPLIER_ROLE` is now granted through the
  timelock on every series, guarded on production, asserted in-band, covered by three
  mutation-checked tests, and verified live on three series.
- **The two Sepolia scripts had no chain guard at all** plus seven further defects (§0);
  all are fixed. Their ERC-8056 and swap logic was otherwise correct.
- No guard was weakened and no ERC-8056 semantics were changed. `forge test`: 511 passed,
  0 failed.
